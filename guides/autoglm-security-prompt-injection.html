Security briefing

Run AutoGLM with explicit boundaries against prompt injection.

A phone agent reads untrusted screens and takes actions. That combination changes the threat model: malicious instructions can appear inside a web page, an app, a message, or an image and attempt to redirect the task.

Published Jul 25, 20265 minute readOperational guidance

Permissions are a security boundary. Official setup documentation asks users to review device permissions carefully.

This is not a vulnerability notice. A July 2026 security report discussed laboratory prompt-injection attacks against open-source Android agents. It does not establish an AutoGLM CVE or a confirmed compromise of every installation. Treat it as a reason to deploy defense in depth.

What can go wrong

Prompt injection is content that tries to change an agent's objective. The injected instruction may be visible text or text rendered in a way intended for a model rather than a person. A phone agent can be exposed while reading a page, a chat, an app listing, or a QR-adjacent instruction. The concern rises when the agent also has access to privileged ADB, a shell, network credentials, or unattended approval flows.

Five controls to use from day one

  1. Use a dedicated device or emulator. Do not connect a development agent to your primary phone, personal accounts, password manager, or production admin session.
  2. Limit the task scope. Give the agent a concrete allowed action list and a stop condition. Treat any instruction found on screen as data, not a new system instruction.
  3. Keep sensitive action confirmation on. Require a human approval gate before sending data, granting permissions, making purchases, changing settings, or opening a shell.
  4. Restrict ADB and remote access. Use trusted USB or a private network, revoke unused debugging authorizations, and do not expose ADB to the public internet.
  5. Log and review. Retain task prompts, screenshots, action traces, and approval records. Stop the run when the plan diverges from the user's stated goal.

Set the permissions boundary before the first run

AllowedOpen a named app, search public content, navigate a pre-approved test flow.
Approval requiredSubmit forms, send messages, install software, make a purchase, or reveal private data.
Never unattendedCredential entry, MFA, account recovery, developer settings changes, and shell commands.

The project documentation already includes sensitive-operation confirmation and manual takeover for login or verification-code scenarios. Keep those gates in the workflow; do not bypass them to improve apparent automation success.

When an agent behaves unexpectedly

  • Terminate the task and disconnect the device from remote debugging.
  • Review the last task prompt, screen capture, and requested action before restarting.
  • Revoke any temporary device authorization or API key that may have been exposed.
  • Reduce the next test to a smaller, reversible, fully observable action.
  • Report reproducible security behavior through the official project's issue or security-contact process rather than publishing credentials or exploit steps.
